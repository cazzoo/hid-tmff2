# Unify T500RS effect lifecycle with T300RS (capture-verified)

## Goal
Make the `tmt500rs` driver (branch `hardening/June-pass`) start/stop effects like
`tmt300rs` — i.e. an effect that is played starts, runs for its `replay.length`, and
**terminates**; new effects do not accumulate on top of old ones. The shared `tmff2`
core lifecycle (upload-once / update-on-change / play-on-start / stop-on-expire) is
already correct and is **not** changed — the divergence is entirely inside `tmt500rs`.

## Root cause (verified against raw `.pcapng`, not just docs)
All evidence below is decoded directly from
`captures/device_const_force_left_start_stop_multiple_times.pcapng`
(link type 249 / USB_LINUX_MMAPPED; FFB commands appear at the tail of each URB):

- **`effect_id` must be `0x00`**, not the per-slot `hw_id`. Raw packets:
  - START = `41 00 41 01` (effect_id `0x00`, command `0x41`, arg `0x01`)
  - STOP  = `41 00 00 01` (effect_id `0x00`, command `0x00`, arg `0x01`)
  The current driver passes `hw_id = logical_id + 1` (1–15) into both the `0x01`
  main builder and `t500rs_send_start`/`t500rs_send_stop` (`tmt500rs.c`:
  `t500rs_logical_to_hw_id`, used at `:1032`/`:1053` and in `t500rs_build_r01_main`).
  Non-zero `effect_id` is documented to make constant force produce **no torque**
  (`docs/FFB_T500RS.md:33-36`) — the primary "behaves differently" symptom.
- **Constant force uses FIXED subtypes**, not indexed. Raw uploads:
  - `0x01` main = `01 00 00 40 27 10 00 ff ff 0e 00 1c 00 00 00`
    → `effect_id=0x00`, type `0x00`, param_sub `0x0e`, env_sub `0x1c`
  - `0x02` envelope = `02 1c …` (fixed `0x1c`)
  - `0x03` level = `03 0e 00 1c`, `03 0e 00 1b`, … (fixed code `0x0e`, live level)
  The current driver runs these through `t500rs_index_to_subtypes` (indexed
  `0x0e+0x1c*idx`), which `docs/FFB_T500RS.md:58-64` says breaks constant level
  updates ("no force felt").
- **Duration is the REAL `replay.length`, not `0xffff`.** The capture's `0x01` packet
  carries a finite duration `27 10` = `0x1027` ≈ 4.1 s. This **contradicts**
  `docs/FFB_T500RS.md:74` ("constant & periodic: 0xffff"). The driver should keep
  programming the real length (current code already does: `duration_ms = length ?: 0xffff`);
  do **not** force `0xffff`. (That doc line is wrong and should be corrected.)
- **The wheel does not reliably auto-stop.** Windows still sends an explicit
  `0x41 STOP` (hence the capture name "start_stop_multiple_times"). The core never
  emits `stop_effect` on auto-expiry (`hid-tmff2.c:432-439` only clears
  `FF_EFFECT_PLAYING`), so on T500RS an effect runs forever until something sends STOP.
  `tmt300rs` is saved only because its `0x89` START carries a `count` the hardware
  auto-stops on; T500RS's `0x41` START has no such field.

## Fix (tmt500rs-only; core untouched — per decision)
1. **`effect_id = 0x00`** in `0x01` main and `0x41` START/STOP. Keep the existing
   init-time autocenter STOP exception that targets fixed ID `15`. Stop deriving
   `effect_id` from `t500rs_logical_to_hw_id`.
2. **Subtype policy:**
   - Constant → fixed `param 0x0e` / `env 0x1c` (ignore index).
   - Periodic / Ramp / Condition → indexed `0x0e + 0x1c*n` / `0x1c + 0x1c*n`
     (n = logical effect id, 0-based). EffectID stays `0x00`.
3. **Duration:** program the real `replay.length` (ms) for all types; use `0xffff`
   only when `length == 0` (infinite). Do **not** force `0xffff`.
4. **Leading STOP on upload:** prepend `T500RS_SEQ_STOP` (id `0x00`) to the
   constant / ramp / condition upload sequences (periodic already has it; matches
   `docs/FFB_T500RS.md:166`).
5. **Driver-side per-effect expiry tracker** in `t500rs_device_entry`
   (chosen model: per-effect array, size `T500RS_MAX_EFFECTS`):
   - Each `play_effect` records `start_time` / `count` / duration from `state`
     (`hid-tmff2.h:54-55`); `stop_effect` clears the entry.
   - A re-arming `delayed_work` sends `t500rs_send_stop(0)` for any finite effect
     whose `(delay + length) * count` has elapsed.
   - STOP must use a **dedicated `kzalloc` DMA-safe buffer + driver-owned spinlock**
     (mirror `set_range`), because it runs outside the core worker and must not
     corrupt the core worker's shared `send_buffer`.
   - Infinite effects (`length == 0`) are never auto-stopped (Linux semantics).
6. **Keep `update_effect` in-place** (only `0x03`/`0x04`/`0x05` param packets, no
   STOP/re-upload) — raw capture confirms `03 0e …` live updates.

## Validation
- Build/load on T500RS; `fftest` / `ffmvforce`:
  - Finite constant/periodic auto-stops after `replay.length`.
  - Multiple effects each stop at their own expiry (no accumulation).
  - Explicit stop (`play(0)`) still works.
  - Live param changes still apply.
- **Capture diff:** byte-compare driver output against
  `captures/t500rs_windows_20251002_235917.pcapng`,
  `captures/t500rs_windows_20251003_225720.pcapng`, and
  `captures/device_const_force_left_start_stop_multiple_times.pcapng`.
  Expect exactly: `41 00 41 01` / `41 00 00 01`, `01 00 00 40 … 0e 00 1c`, `03 0e`,
  `02 1c`. Mandatory pre-merge since changing `effect_id`/`subtypes` alters currently
  "working" behavior.

## Risks / open questions
- **STOP(0) is global** (single `effect_id` slot). With a per-effect array, expiring
  effect A's `STOP(0)` may also stop a still-running effect B unless the wheel
  isolates by subtype (unverified). Validate; fallback: only send `STOP(0)` when no
  other effect is active.
- **Periodic frequency units:** `docs/T500RS_FFBEFFECTS.md` says period (ms) while
  `docs/FFB_T500RS.md` says Hz*100 — separate bug, out of scope; flag for its own fix.
- **Doc correction:** `docs/FFB_T500RS.md:74` `0xffff` claim is wrong (capture shows
  real finite duration) — fix the doc alongside the driver change.
- **No hardware in this environment:** validation must be performed by an
  implementation-capable agent on real T500RS hardware.
